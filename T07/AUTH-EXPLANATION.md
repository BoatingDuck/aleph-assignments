# T07 인증 구현 설명

## 1. 무엇을 사용했는가

아이디와 비밀번호를 사용하는 자체 회원가입·로그인 방식을 구현했다.

비밀번호는 `bcryptjs`를 사용해 bcrypt 방식으로 해시한 뒤 PostgreSQL 데이터베이스에 저장한다. 평문 비밀번호는 데이터베이스에 저장하지 않는다.

로그인에 성공하면 서버에서 무작위 세션 토큰을 생성한다. 브라우저에는 `t07_session` 쿠키를 저장하고, 데이터베이스에는 원본 토큰 대신 SHA-256으로 해시한 값과 사용자 ID, 만료 시각을 저장한다.

세션 쿠키에는 `HttpOnly`, `SameSite=Lax`, `Path=/`를 적용했으며 운영 환경에서는 `Secure` 속성을 사용한다. 세션 유효기간은 24시간이다.


## 2. 왜 이 방식을 사용했는가

T07에서는 사용자마다 자신의 자료만 볼 수 있어야 하므로 각 요청에서 로그인 사용자를 식별할 방법이 필요했다.

비밀번호를 평문으로 저장하면 데이터베이스가 노출되었을 때 사용자의 실제 비밀번호까지 바로 노출될 수 있기 때문에 bcrypt 해시를 사용했다. bcrypt는 같은 비밀번호라도 매번 다른 salt가 적용되어 서로 다른 해시값이 만들어진다.

세션 토큰은 URL에 포함하지 않고 쿠키로 전달하도록 했다. 또한 브라우저에 저장되는 원본 세션 값과 데이터베이스에 저장되는 값을 분리하기 위해 데이터베이스에는 세션 토큰의 SHA-256 해시만 저장하도록 했다.


## 3. 어디를 어떻게 수정했는가

인증 기능은 주로 다음 위치에 구현했다.

- `lib/password.ts`
  - bcrypt를 이용한 비밀번호 해시와 검증을 담당한다.
  - bcrypt cost 값은 12를 사용한다.

- `lib/auth.ts`
  - 로그인 세션 생성, 세션 조회, 현재 사용자 확인, 세션 폐기를 담당한다.
  - 무작위 세션 토큰을 생성하고 데이터베이스에는 토큰의 해시만 저장한다.

- `app/api/auth/signup/route.ts`
  - 회원가입을 처리한다.
  - 중복 아이디를 차단하고 비밀번호를 해시한 뒤 사용자 정보를 저장한다.

- `app/api/auth/login/route.ts`
  - 아이디와 비밀번호를 검증하고 로그인 세션을 생성한다.
  - 존재하지 않는 아이디와 잘못된 비밀번호는 같은 오류 메시지를 반환한다.

- `app/api/auth/logout/route.ts`
  - 현재 세션을 데이터베이스에서 제거하고 브라우저의 세션 쿠키를 만료시킨다.

- `app/api/auth/me/route.ts`
  - 현재 요청이 인증된 사용자의 요청인지 확인한다.

- `app/api/auth/change-password/route.ts`
  - 비밀번호를 변경하고 기존 세션을 모두 폐기한다.

- `app/api/auth/delete-account/route.ts`
  - 현재 비밀번호를 다시 확인한 뒤 계정과 연결된 자료를 삭제한다.

계획, 할 일, 실행 기록, 돌아보기, 관찰 기록 등의 API에서도 현재 로그인한 사용자의 ID를 기준으로 데이터를 조회·수정·삭제하도록 변경했다.


## 4. 로그인하지 않은 접근이 실패한다는 근거

로그인한 상태에서 `GET /api/auth/me`를 요청하면 현재 로그인한 사용자의 정보가 정상적으로 반환된다.

로그아웃한 뒤 동일한 URL과 동일한 GET 방식으로 다시 요청하면 다음과 같이 인증 실패 응답이 반환된다.

- HTTP 상태: `401`
- 응답: `로그인이 필요합니다.`

시크릿 창에서도 결과물 주소에 처음 접속하면 로그인 화면이 먼저 표시되고, 로그인하기 전에는 계획·할 일·실행 기록 등 실제 자료가 표시되지 않는 것을 확인했다.

또한 인증되지 않은 상태에서 자료 API를 직접 호출해도 자료를 반환하지 않도록 처리했다.


## 5. AI와 내가 각각 판단한 부분

AI에게는 인증 구조를 설계하고 bcrypt 비밀번호 저장, 세션 처리, 사용자별 자료 접근 제어에 필요한 코드 작성과 점검을 맡겼다.

나는 실제 두 계정을 만들어 서로의 자료를 읽기·수정·삭제할 수 없는지 직접 확인하고, 로그아웃·비밀번호 변경·계정 삭제 후 기존 인증 정보가 더 이상 사용할 수 없는지 판단했다.

또한 실제 기능 오류가 없는 상태에서 불필요한 변경을 추가하지 않았으며, 배포 환경에서 로그인 화면과 사용자별 데이터 분리가 실제로 동작하는지를 직접 확인한 뒤 반영 여부를 결정했다.


## 6. 아직 보호하지 못한 부분

로그인 실패 횟수 제한이나 일정 횟수 이상 실패했을 때의 계정 잠금 기능은 아직 구현하지 않았다.

따라서 공격자가 하나의 아이디에 대해 많은 비밀번호를 반복해서 시도하는 무차별 대입 공격을 서버 차원에서 충분히 제한하지 못한다는 위험이 남아 있다.

현재 비밀번호는 bcrypt로 보호하고 인증 실패 시 존재하지 않는 아이디와 잘못된 비밀번호에 동일한 메시지를 반환하지만, 실제 서비스로 확장한다면 로그인 요청에 대한 rate limiting이나 일시적 계정 잠금 같은 추가 보호가 필요하다.
