# T07 인증 구현 설명

<br>

## 1. 무엇을 사용했는가

아이디와 비밀번호를 사용하는 자체 회원가입·로그인 흐름을 구현하고, 비밀번호 처리는 널리 쓰이는 라이브러리에 맡겼다.

비밀번호 해시에는 `bcryptjs` 버전 `^3.0.3`을 사용했으며, bcrypt cost 값은 12로 설정했다. 입력한 비밀번호는 bcrypt 해시로 변환한 뒤 PostgreSQL 데이터베이스에 저장하며 평문 비밀번호는 저장하지 않는다.

로그인에 성공하면 서버에서 무작위 세션 토큰을 생성한다. 브라우저에는 `t07_session` 쿠키를 저장하고, 데이터베이스에는 원본 세션 토큰 대신 SHA-256으로 해시한 값과 사용자 ID, 만료 시각을 저장한다.

세션 쿠키에는 `HttpOnly`, `SameSite=Lax`, `Path=/`를 적용했으며 운영 환경에서는 `Secure` 속성을 사용한다. 세션 유효기간은 24시간이다.

즉 인증 흐름 자체는 애플리케이션에서 구현하고, 비밀번호를 안전하게 해시하고 검증하는 부분은 `bcryptjs` 라이브러리에 맡겼다.

<br>

## 2. 왜 이 방식을 사용했는가

T07에서는 단순히 로그인 화면을 만드는 것보다 로그인한 사용자에게 자기 자료만 보이게 하는 것이 더 중요하다고 생각했다. 그래서 요청이 들어올 때마다 현재 로그인한 사용자를 확인할 수 있도록 서버에서 세션을 관리하는 방식을 선택했다.

처음에는 Auth.js처럼 인증을 맡길 수 있는 방법도 검토했다. 하지만 이번 과제에서는 로그인과 로그아웃뿐 아니라 세션이 어떻게 만들어지고 없어지는지, 비밀번호를 바꾼 뒤 기존 세션이 실제로 막히는지, 다른 사용자의 자료 요청이 서버에서 거절되는지까지 직접 확인해야 했다. 그래서 이번에는 이 과정을 코드에서 직접 확인하기 쉬운 서버 측 세션 방식을 사용했다.

비밀번호는 직접 암호화 로직을 만드는 대신 `bcryptjs`를 사용했다. 평문 비밀번호를 저장하지 않으면서 검증할 수 있고, 같은 비밀번호를 사용해도 매번 같은 해시가 만들어지지 않는다는 점도 확인할 수 있었기 때문이다.

세션 값은 주소에 넣지 않고 쿠키로 전달하도록 했다. 데이터베이스에도 브라우저가 가진 원본 세션 값을 그대로 저장하지 않고 SHA-256 해시만 저장하도록 해서, DB에 있는 값만으로 원본 세션을 바로 사용할 수 없게 했다.

<br>

## 3. 어디를 어떻게 수정했는가

인증은 한 파일에 몰아넣지 않고 역할별로 나눠서 붙였다.

`lib/password.ts`에서는 bcrypt를 이용한 비밀번호 해시와 검증을 처리한다. bcrypt cost는 12로 두었다.

`lib/auth.ts`에서는 세션 생성과 확인, 로그아웃 처리를 맡긴다. 로그인에 성공하면 무작위 세션 값을 만들고, DB에는 원본 대신 SHA-256 해시를 저장한다. 세션이 없거나 만료된 경우에는 로그인한 사용자로 인정하지 않는다.

회원가입, 로그인, 로그아웃, 현재 사용자 확인은 각각 아래 API에서 처리한다.

- `app/api/auth/signup/route.ts`
- `app/api/auth/login/route.ts`
- `app/api/auth/logout/route.ts`
- `app/api/auth/me/route.ts`

비밀번호 변경은 `app/api/auth/change-password/route.ts`에서 처리하고, 변경이 끝나면 기존 세션을 모두 없애도록 했다. 계정 삭제는 `app/api/auth/delete-account/route.ts`에서 현재 비밀번호를 다시 확인한 뒤 처리한다.

첫 화면도 인증 여부에 따라 나눴다. `app/page.tsx`에서 현재 사용자를 확인하고, 로그인하지 않은 상태라면 `AuthScreen`만 보여 주고 로그인된 경우에만 실제 다이어리 화면인 `AuthenticatedApp`을 보여 준다.

T06에서 사용하던 자료 API도 그대로 두지 않고 사용자 기준을 붙였다. `plans`, `tasks`, `executions`, `reflection`, `tracking-config`, `export` API에서 현재 로그인한 사용자를 먼저 확인하고, 조회·수정·삭제할 때도 그 사용자의 자료만 대상으로 하도록 바꿨다.

그래서 주소나 요청값에 다른 사용자의 자료 ID를 넣더라도 서버에서 현재 로그인 사용자와 연결되지 않은 자료라면 읽거나 수정할 수 없도록 했다.

<br>

## 4. 로그인하지 않거나 다른 계정의 자료에 접근하지 못한다는 것을 확인한 기록

배포된 환경에서 로그인 상태와 계정 A/B를 바꿔 가며 직접 요청해 확인했다. 테스트할 때 사용한 비밀번호와 세션 값은 기록에 남기지 않았다.

| 확인 내용 | 정상 요청 | 거절 요청 |
| --- | --- | --- |
| 로그인 상태 확인 | 로그인 후 `GET /api/auth/me` → `200` | 로그아웃 후 같은 `GET /api/auth/me` → `401` |
| 비로그인 자료 요청 | 로그인 후 `GET /api/plans` → 내 자료 반환 | 로그아웃 후 같은 `GET /api/plans` → `401` |
| 다른 계정 자료 읽기 | A가 A의 테스트 자료를 조회 → 정상 | A가 B의 자료 ID로 조회 → `404` |
| 다른 계정 자료 수정 | A가 A의 테스트 자료를 수정 → 정상 | A가 B의 자료 ID로 수정 → `404` |
| 다른 계정 자료 삭제 | 테스트 계정이 자기 테스트 자료를 삭제 → 정상 | A가 B의 자료 ID로 삭제 → `404` |

A와 B의 역할을 바꿔서도 같은 방식으로 확인했고, B에서 A의 자료를 읽거나 수정하거나 삭제하려는 요청도 모두 거절되었다.

URL, 요청 헤더, 요청 본문에 다른 사용자를 가리키는 값을 넣는 경우도 확인했다. 이런 값을 임의로 넣어도 소유자 판단에는 사용되지 않았고, 서버 세션에서 확인한 현재 로그인 사용자의 자료만 반환되었다. 목록 API에서도 상대 계정의 자료는 나오지 않았다.

거절 전후에 상대 계정의 자료 건수와 내용도 다시 확인했으며, 실패한 요청 때문에 자료가 수정되거나 삭제되거나 새로 생긴 경우는 없었다.

이 접근 제한은 `app/api/plans`, `app/api/tasks`, `app/api/executions`, `app/api/reflection` 등의 API에서 현재 로그인한 사용자를 확인하고 그 사용자가 소유한 자료만 대상으로 조회·수정·삭제하도록 한 부분에서 처리한다.

<br>

## 5. AI와 내가 각각 판단한 부분

AI에게는 인증 구조를 정리하고 회원가입, 로그인, 세션 처리, 비밀번호 해시, 사용자별 자료 접근 제한에 필요한 코드 작성과 점검을 도움받았다.

나는 실제 배포된 환경에서 회원가입과 로그인, 로그아웃, 비밀번호 변경, 계정 삭제를 직접 해봤고, 테스트 계정 두 개를 만들어 서로의 자료에 접근할 수 없는지도 직접 확인했다. 5일 기록과 계획 규칙 변경처럼 과제 기준에 맞게 유지해야 하는 부분도 직접 확인하면서 진행했다.

AI가 확인 과정에서 수정할 부분을 제안하더라도 실제 기능에 문제가 없거나 과제 조건과 맞지 않는 경우에는 그대로 반영하지 않았다. 실제로 확인한 결과를 기준으로 필요한 수정만 적용했다.

<br>

## 6. 아직 보호하지 못한 부분

현재 로그인 요청에는 실패 횟수 제한이나 일정 횟수 이상 실패했을 때 잠시 로그인을 막는 기능이 없다.

비밀번호 자체는 bcrypt로 저장하고, 존재하지 않는 아이디와 틀린 비밀번호에도 같은 오류 메시지를 보여 주도록 했지만 이것만으로 반복적인 로그인 시도 자체를 막을 수는 없다.

그래서 누군가 한 계정을 대상으로 비밀번호를 계속 시도하는 무차별 대입 공격에는 아직 약점이 남아 있다. 실제 서비스로 더 확장한다면 로그인 요청 횟수를 제한하거나 일정 시간 동안 로그인을 막는 기능을 추가할 필요가 있다.
