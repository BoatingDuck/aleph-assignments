# T08 인증 구현 설명서

> 최종 정리: 2026-10-21. 이 문서는 구현 후 실제로 관찰한 결과를 기록한 것입니다. 아이폰에서 확인한 로그인과 PC Chrome 가상 인증기를 사용한 보안 실험은 서로 구분했습니다. 기록되지 않은 시험을 통과했다고 쓰지 않았습니다.

## ① 어떤 인증을 사용했나

비밀번호 대신 **WebAuthn/FIDO2 패스키**를 사용했습니다. 브라우저에는 `@simplewebauthn/browser@13.2.2`, 서버에는 `@simplewebauthn/server@13.2.2`를 사용하며, 서명 알고리즘을 직접 구현하지 않았습니다.

- **공개 소개:** 기존 T01 소개는 로그인 없이 열립니다. 아래의 T08 비공개 자리만 잠금 상태로 시작합니다.
- **실습 계정:** `owner`와 `reviewer` 두 계정이며, 각각 서로 다른 가상 기록 3건이 Supabase PostgreSQL에 있습니다.
- **패스키 등록:** 서버가 일회용 등록 질문(challenge)을 발급하고, 기기는 등록 응답을 생성합니다. 서버는 Origin·RP ID·사용자 확인을 검증하고 **COSE 공개키, credential ID, 카운터, 이름, 등록일**을 저장합니다. 개인키를 받거나 저장하는 API·DB 열은 없습니다.
- **패스키 로그인:** 서버는 매번 새 질문을 발급하고 등록된 공개키로 서명을 검증합니다. 성공하면 서버에서 12시간 세션을 만들며, 쿠키에는 `HttpOnly; SameSite=Strict; Secure`를 적용합니다.
- **저장 위치:** 실제 owner와 reviewer 패스키는 아이폰의 **암호(Passwords) 앱**에서 각각 확인했습니다. 서버가 아닌 PC의 가상 인증기에 생성한 검사용 패스키는 서명 실험 후 삭제했습니다.
- **주의:** 동기화형 패스키는 제공업체의 암호화된 동기화 기능을 사용할 수 있습니다. 따라서 “서버에 개인키를 보내지 않는다”와 “기기 사이에서도 이동하지 않는다”는 같은 뜻이 아닙니다.

## ② 왜 이 방식을 선택했나

처음에는 PC에서 패스키로 로그인할 때 Windows의 USB 보안키 선택창이 나와 인증을 끝낼 수 없었습니다. 기존 패스키는 아이폰에 있었고, 로그인 시마다 PC의 USB 인증 절차에 의존하는 방식은 과제를 반복 검증하기에도 불편했습니다.

그래서 **PC는 QR을 표시하고, 아이폰은 자신에게 저장된 패스키로 승인한 뒤, 로그인 세션은 PC에 발급하는 흐름**으로 수정했습니다. QR을 스캔했다고 곧바로 로그인시키는 것이 아니라, 휴대전화에서 다시 WebAuthn 서명을 검증해야 승인됩니다. 이 방식은 과제에서 요구하는 패스키·공개키 기반 검증을 유지하면서 실제 사용 기기의 제약을 해결합니다.

아이폰에서는 일반 로그인·Face ID 승인·PC 연결까지 직접 확인했습니다. 다만 아이폰 Safari만으로 서명 원본을 복사한 뒤 한 비트 수정하거나 동일 JSON을 재전송하는 실험은 진행하기 어려웠습니다. 단축어 방식도 시도했지만 안정적으로 검사 결과를 얻지 못해 사용하지 않았습니다. **이 제한을 숨기지 않고**, PC Chrome DevTools의 *WebAuthn 가상 인증기*를 이용해 별도의 시험용 패스키를 발급하고 **실제 운영 API에 서명 검증 요청**을 보내 C30·C31·C45를 측정했습니다. 가상 인증기 시험을 아이폰 실측이라고 적지 않았습니다.

## ③ 무엇을 어떻게 구현했나

| 구분 | 소스·구현 | 서버의 확인 기준 |
| --- | --- | --- |
| 공개/비공개 구분 | `scripts/sync-t01.mjs`, `snippets/private-room.html`, `public/index.html` | T01 원본 공개 영역은 유지, 비공개 내용은 HTML에 넣지 않음 |
| 등록 | `src/passkey-client.js` → `registration-options` / `registration-verify` | 등록 초대 또는 현재 세션, 질문·Origin·RP ID·사용자 확인 검사 후 공개키 저장 |
| 일반 로그인 | `authentication-options` / `authentication-verify` | 계정에 등록된 공개키로 서명 검증, 인증 질문 1회 소비 후 세션 발급 |
| PC QR 로그인 | `phone-start` / `phone-prepare` / `phone-approve` / `phone-poll` | PC 전용 쿠키와 QR 토큰을 서로 분리, 3분 만료, 휴대전화 서명 검증 후 PC만 세션 수령 |
| 로그아웃 | `logout` / `t08_sessions.revoked_at` | 서버 세션을 철회하여 기존 쿠키 재사용 차단 |
| 내 기록 조회 | `GET /api?action=notes` | 요청자가 전한 account 값이 아닌 로그인 세션의 계정 ID로만 조회 |
| 다른 계정 요청 | `GET /api?action=account-notes&account=...` | 상대 계정일 때 403 |
| 패스키 삭제 | `passkey-delete` | 등록 목록에서 제거, 마지막 하나는 409로 삭제 방지 |

Supabase는 `t08_accounts`, `t08_notes`, `t08_passkeys`, `t08_invites`, `t08_challenges`, `t08_sessions`, `t08_phone_logins` **7개** 테이블을 사용합니다. 테이블의 RLS가 켜져 있고 브라우저의 `anon` / `authenticated` 역할에는 직접 조회 권한을 주지 않습니다. 서버의 데이터베이스 연결 문자열은 환경변수로만 사용합니다.

## ④ 실제로 어떻게 확인했나

### 준비: 비밀번호 없는 화면, 두 계정, 공개키

로그인하지 않은 상태에서도 T01 소개 화면이 HTTP 200으로 열리는 것을 확인했습니다. 공개 HTML에 가상 비공개 기록 본문이 들어 있지 않으며, owner와 reviewer가 로그인한 뒤 각각 자기 기록 3건을 확인했습니다. DB에서도 **owner 3건·reviewer 3건**이 유지됩니다.

운영 DB에서 등록 질문은 **17개 모두 서로 다른 값**, 로그인 질문은 **48개 모두 서로 다른 값**임을 확인했습니다. 이는 질문 원문을 공개하지 않은 DB 집계 증거이며, 각각 2건의 원문을 나란히 찍은 화면 증거와는 구별됩니다. 두 계정에 유효한 공개키가 저장되어 있고, 최종 상태에서는 **각각 패스키 1개**가 남아 있습니다. 공개키의 인코딩 길이는 각 103자로 확인했습니다.

가상 인증기로 패스키를 추가 등록할 때 `registration-verify`의 Network Request Payload를 확인했습니다. 캡처에는 `challengeId`, `label`, `response`, `id`, `rawId`, `type: public-key` 등이 보였고 개인키 필드는 보이지 않았습니다. 다만 `response` 일부 하위 항목은 펼치지 않았기 때문에 **캡처 한 장만으로 전체 속성의 부재를 입증했다고 주장하지 않습니다**. 서버는 등록 응답을 검증한 뒤 공개키만 DB에 저장합니다.

### 필수 재현 검사 1 — 잠금 확인

로그인 상태에서 `GET /api?action=notes`를 보내면 **HTTP 200 / 본인 기록 3건**입니다. 로그아웃 후 이전 세션 쿠키를 그대로 사용하는 요청에서는 **HTTP 401 Unauthorized**와 오류 메시지만 반환되는 것을 확인했습니다(C33). 공개 페이지와 비공개 API를 구분하는 이유는 화면에서 감추는 것만으로는 인증이 되지 않기 때문입니다.

### 필수 재현 검사 2 — 계정 격리

owner 로그인 상태에서 reviewer 기록 조회는 **403**, reviewer 로그인 상태에서 owner 기록 조회도 **403**으로 거절됐습니다. 양방향 검사 전후 본인 자료 조회는 **200 / 3건**이었으며, DB의 각 계정 기록 수도 3건으로 그대로 유지됐습니다(C39). 추가로 C40에서 reviewer 로그인 세션으로 정상 GET, `?account=owner`를 넣은 GET, `{"account":"owner"}`를 넣은 POST를 각각 실행했습니다. 세 요청 모두 **HTTP 200 / 실제 소유자 reviewer / 기록 3건**으로 응답했습니다. 즉 입력한 `owner`가 무시되고 인증된 reviewer의 자료만 반환됨을 실제 응답과 캡처로 확인했습니다.

### 필수 재현 검사 3 — 서명 변조·질문 재사용

아이폰에 저장된 패스키로 실제 로그인이 되는 것을 먼저 확인했습니다. **추가적인 실패 요청 실험은 PC Chrome 가상 인증기로 따로 진행했습니다.** 브라우저가 생성한 정상 서명의 마지막 바이트를 한 비트 바꾸어 운영 `authentication-verify`에 전송하자 **403**, 변조 전 정상 응답은 **200**, 똑같은 `{challengeId,response}`를 한 번 더 보내자 **409**였습니다(C30·C31). 세 요청 모두 실제 운영 API의 HTTP 결과입니다. 가상 인증기 실험 결과를 아이폰의 서명 변조 실측으로 바꾸어 서술하지 않았습니다.

### 필수 재현 검사 4 — 패스키 삭제 뒤 접근

reviewer 계정의 `테스트 패스키`와 `테스트2 패스키` 두 개를 확인한 후, 사용 기록이 없던 두 번째 키를 삭제했습니다. 서버의 등록 개수는 **2→1**, 남은 아이폰 패스키로 다시 로그인했을 때 가상 기록 **3건**이 보였습니다(C44).

이어서 가상 인증기로 새 시험용 키를 만들어 서명 응답을 확보하고, **그 키만** 서버에서 삭제(**200**)한 뒤 삭제된 ID와 서명을 제출하자 **403**으로 거절됐습니다(C45). 마지막 키를 삭제하는 시도는 **409**, 남은 키는 계속 **1개**였습니다(C46). 최종 DB 조회에서도 두 계정의 패스키 1개씩과 기록 3건씩을 확인했습니다.

### 기타 실제 결과

- **C25:** 추가 등록 중 인증을 취소했을 때 화면에 취소 안내가 나오고 패스키 수가 증가하지 않았습니다.
- **PC↔아이폰 QR:** 실제 아이폰 승인을 통해 PC 화면이 자동 로그인되고 기록 3건이 표시됐습니다. 서버 DB에서도 PC가 승인 연결을 소비한 기록 2건을 확인했습니다.
- **자동 회귀 검사:** T08 GitHub Actions에서 Node.js 22로 빌드·검사 **31/31 PASS**. 이 결과는 실제 기기 실험과 별개로 기록했습니다.

검사에 사용한 서명 원문, 세션 쿠키, QR 토큰, 초대 주소, 데이터베이스 비밀번호는 제출 문서에 포함하지 않았습니다. 수행 결과와 미실측 범위는 [검사결과](검사결과_2026-10-21.md)에 따로 정리했습니다.

## ⑤ AI와 나의 판단

- **AI에게 맡긴 일:** WebAuthn 서버·브라우저 코드와 Supabase 연동, PC QR 로그인 구현안, 검사 스크립트와 문서 초안을 만드는 데 도움을 받았습니다.
- **직접 판단한 일:** PC에서 USB 인증 방식을 반복하는 대신 기존 아이폰 패스키를 활용한 QR 승인을 선택했습니다. 아이폰에서 승인을 눌러 PC 로그인이 되는지, 기록이 실제로 보이는지, 개발자 도구에서 401·403·409가 나오는지를 직접 실행하고 확인했습니다.
- **제안을 따르지 않은 일:** Windows USB 보안키 선택창을 계속 이용하거나 아이폰 단축어로 인증 검사를 진행하는 방법은 실제 사용·재현이 불편해서 유지하지 않았습니다. 대신 QR 로그인과 Chrome 가상 인증기의 별도 시험용 키로 인증을 검증했습니다. AI가 작성한 코드라도 검사를 통과하지 않은 결과를 성공했다고 적지 않았습니다.

## ⑥ 아직 막지 못한 것

현재 구현에는 패스키를 모두 잃어버렸을 때 본인 확인을 거쳐 복구하는 독립된 절차가 없습니다. 마지막 키 삭제 금지는 실수로 전부 삭제하는 상황만 줄입니다. 실제 사용자 기기의 분실·고장을 막지는 못하며, 별도의 안전한 백업 수단이 필요합니다.

서버 측 IP별 로그인 시도 횟수 제한, 지속적인 감사 로그, 운영 환경의 별도 침해 탐지·알림은 구현하지 않았습니다. 대규모 상용 서비스 수준의 방어를 제공한다고 주장하지 않습니다. C23 등록 요청 캡처에서 일부 하위 필드를 펼치지 못했고, 패스키 0개 계정의 로그인 실패 응답은 실측하지 않았습니다. 반면 C40 계정 위조 GET·POST 요청의 개별 HTTP 응답은 실측했고 캡처를 보존했습니다.
