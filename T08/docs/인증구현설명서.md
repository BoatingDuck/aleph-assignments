# T08 인증 구현 설명서

> **제출 전 필수:** 아래 `[실측 입력]`은 실제 배포·기기·DB·네트워크 응답을 확인한 후 채웁니다. 이 문서는 처음에 기록 양식으로 작성되었습니다. 2026-10-21의 완료된 실제 검사 증거는 문서 하단과 검사결과_2026-10-21.md에 보완 기록했습니다. 일부 초기 입력 양식은 당시의 기록입니다. 실제 초대 링크, DB 접속 문자열, 세션 쿠키·토큰, 개인키, 실제 개인정보를 제출물에 붙여 넣지 마세요. 공개키(서버 보관값)는 공개 정보이므로 기록할 수 있습니다.

## ① 무엇으로 붙였나

- 방식: **라이브러리 기반 WebAuthn/FIDO2 패스키**. `@simplewebauthn/server@13.2.2`와 `@simplewebauthn/browser@13.2.2` 사용. 직접 암호·서명 알고리즘을 구현하지 않음.
- 서버: Vercel Node.js 함수 `api/index.js`, 브라우저: `src/passkey-client.js`를 esbuild로 번들링하여 `public/passkey-client.js`로 배포.
- 데이터: Supabase PostgreSQL. 패스키 식별자, COSE 공개키의 base64url 인코딩, 서명 카운터, 지원 전송 수단, 이름과 등록일만 영구 저장. **개인키·로그인 비밀번호·비밀번호 해시는 저장하지 않음.**
- 초기 신뢰 확보: 서버 관리자가 10분·1회용 **최초 등록 초대 URL**을 발급. 초대 링크는 로그인 수단이 아니라 최초 소유자의 패스키를 묶기 위한 부트스트랩 수단으로 사용되며, 사용 후 만료됨.
- 세션: 로그인 이후 12시간 만료되는 서버측 불투명 세션. 클라이언트 쿠키는 `HttpOnly`, `SameSite=Strict`, HTTPS면 `Secure`; DB에는 세션값의 SHA-256 해시만 저장.
- **개인키 범위:** 개인키는 이 웹사이트의 서버에 전송되거나 저장되지 않습니다. 다만 Google 비밀번호 관리자 같은 동기화형 패스키는 제공업체에 의해 암호화된 형태로 기기 간 동기화될 수 있으므로 “무조건 기기 외부로 나가지 않는다”고 단정하지 않습니다.
- 실제 패스키 저장 위치: **[실측 입력: Google 비밀번호 관리자 / 기기 자체 / 보안 키]**. 두 번째 패스키 저장 위치: **[실측 입력]**.

## ② 왜 그걸 골랐나

비밀번호 보관·재설정·입력 위험을 없애고, 기기의 개인키로 서버의 **새 일회용 질문(challenge)** 에 서명하도록 하기 위해 WebAuthn을 선택했습니다. 공개키로 서명을 확인하면, 개인키를 받지 않고 소유 증명을 검증할 수 있습니다. 직접 암호 코드를 작성하지 않고 검증된 라이브러리의 Origin·RP ID·서명 검증을 이용했습니다. Stateless 서버리스 인스턴스 간에도 질문 재사용을 차단하도록 DB의 원자적 상태 변경을 적용했습니다.

## ③ 어디를 어떻게 고쳤나

T01의 기존 공개 소개(히어로·세 가지 강점·연구·LMS·공개 범위)는 공개 상태로 유지합니다. `scripts/sync-t01.mjs`가 기존 `../T01`의 원본을 복사해 `#private-room` 섹션만 추가합니다. `public/index.html` 및 `public/passkey.css`는 공개/비공개 경계, 로그인 상태와 패스키 목록 UI를 제공합니다. 실제 가상 비공개 자료는 `scripts/init-db.mjs`가 DB에 생성하며 **HTML이나 JS 번들에 포함되지 않습니다.**

| 흐름 | 브라우저 소스 | 서버 소스·DB | 권한 경계 |
| --- | --- | --- | --- |
| **등록** | `src/passkey-client.js` `register()` → `startRegistration()` | `api/index.js` `registrationBegin()`, `registrationFinish()` → `t08_challenges`, `t08_invites`, `t08_passkeys` | 일회용 등록 초대 또는 현재 계정 세션 → challenge/Origin/RP ID/사용자 확인 검증 → 공개키 저장 |
| **로그인** | `src/passkey-client.js` 로그인 버튼 → `startAuthentication()` | `api/index.js` `loginBegin()`, `loginFinish()` → `t08_challenges`, `t08_passkeys`, `t08_sessions` | 등록된 계정의 공개키로 서명 확인 → 단 한 번만 challenge 사용 → 세션 발급 |
| **로그아웃** | `src/passkey-client.js` 로그아웃 버튼 | `api/index.js` `logout()` → `t08_sessions.revoked_at` | 서버 세션을 무효화하고 쿠키 만료 |
| **비공개 자료 조회** | `src/passkey-client.js` `refresh()` → `request('notes')` | `api/index.js` `getSession()`, `ownNotes()` → `t08_notes` | 세션 계정 ID로만 DB 조회; 직접 GET/POST도 401/403 |
| **타인 자료 직접 요청** | DevTools/검사 요청 | `api/index.js` `action==='account-notes'`, `requireOwnAccount()` | 타인 계정이면 **403**; 자기 계정과 일치할 때만 반환 |
| **패스키 삭제** | `src/passkey-client.js` `drawKeys()` | `api/index.js` `deleteKey()` → `t08_passkeys` | 로그인한 계정의 키만 삭제; 마지막 키 삭제 409 |

등록 중 취소하면 브라우저에 취소 메시지가 나타나고 검증 완료 요청 및 DB `t08_passkeys` 삽입은 진행되지 않습니다. 요청 본문에는 공개키·attestation/assertion 응답만 있으며 개인키 데이터는 없습니다.

### 네 가지 필수 재현 검사 (성공 요청 + 거절 요청)

**1) 로그인 없이 비공개 주소 직접 열기**

- 성공 요청(로그인 후): `GET /api?action=notes` → 예상 `200`, **내 계정의 가상 메모 3건**
- 거절 요청(시크릿 무로그인): `GET /api?action=notes` → 예상 `401`, `{"error":"패스키 로그인 후 확인할 수 있습니다."}`
- 시크릿 HTML 원문 `view-source:https://.../`: 공개 T01 콘텐츠만 있고 가상 메모 문장은 없음
- `[실측 입력: 시각 / 요청 / 성공 응답 / 401 응답 / 페이지 소스 검사]`

**2) 남의 패스키/세션으로 상대 계정 자료 열기 (양방향)**

- owner 세션 + 성공: `GET /api?action=account-notes&account=owner` → 예상 `200`, owner 3건
- owner 세션 + 거절: `GET /api?action=account-notes&account=reviewer` → 예상 `403`, `다른 계정의 자료는 조회할 수 없습니다.`
- reviewer 세션 + 성공: `GET /api?action=account-notes&account=reviewer` → 예상 `200`, reviewer 3건
- reviewer 세션 + 거절: `GET /api?action=account-notes&account=owner` → 예상 `403`
- 요청 바디로 소유자 위조: owner로 로그인하고 `POST /api?action=notes`의 JSON 본문을 `{"account":"reviewer"}`로 보내기 → 예상 `200`이더라도 `owner` 자신의 3건만 반환
- 요청 주소로 소유자 위조: owner 로그인 중 `GET /api?action=notes&account=reviewer` → 예상 `200`이더라도 owner 자신의 3건만 반환
- 건수 고정: 공격 전/후 반대쪽 자료 3건 → 3건; 읽기·거절은 기록을 변경하지 않음
- 거절 코드: `api/index.js`의 `action==='account-notes'`와 `requireOwnAccount()`
- `[실측 입력: 양방향 성공/실패 네 건, 주소/본문 위조 두 건, 전후 건수 및 시각]`

**3) 이미 사용한 로그인 질문 재사용**

- 성공 요청: owner에 대해 `POST /api?action=authentication-options`로 질문 A를 받고, 기기 서명으로 `POST /api?action=authentication-verify` → 예상 `200` (쿠키 값은 **전부 가림**)
- 실패 요청: 동일한 `challengeId`와 동일한 이미 사용된 서명 JSON을 다시 `POST /api?action=authentication-verify` → 예상 `409`, `이미 사용했거나 만료된 로그인 질문입니다.`
- 새 질문: 다시 `authentication-options` 요청해 질문 B 발급 → 반드시 A와 달라야 함
- 위조 서명: 새 질문에 대해 미등록 credential ID 또는 임의 서명을 제출 → 예상 `403`
- `[실측 입력: A/B의 다른 질문값, 성공 응답, 재사용 409 응답, 위조 403 응답, 시각]`

**4) 패스키 1개 삭제한 뒤 로그인**

- 먼저 owner에 패스키 2개를 등록하고 이름/등록일 기록.
- A 패스키 삭제: 로그인한 상태에서 `POST /api?action=passkey-delete` → 예상 `200`
- 로그아웃 후 B 패스키 로그인 → 예상 `200` 및 `GET /api?action=notes` 응답 owner 자료 3건
- 삭제된 A 패스키로의 인증 → 예상 `403` (기존 credential ID를 직접 제시하는 검증 요청). 브라우저의 선택 화면에는 이미 삭제된 A가 보일 수 있지만, 서버의 `allowCredentials` 목록에는 A가 더 이상 존재하지 않음
- 마지막 남은 B 삭제 시도 → 예상 `409`와 마지막 키 삭제 금지 안내
- `[실측 입력: 두 키 목록 / 삭제 200 / 남은 키 로그인 200 / 삭제한 키 403 / 마지막 삭제 409]`

### 로그아웃 뒤 세션 값 재사용

- 성공 요청(로그아웃 전): 같은 쿠키 세션으로 `GET /api?action=notes` → 예상 `200`
- 로그아웃 요청: `POST /api?action=logout` → 예상 `200` 및 서버 DB 세션 `revoked_at` 기록
- 실패 요청(옛 쿠키 재사용): 원래 세션 쿠키를 재전송한 `GET /api?action=notes` → 예상 `401`. **제출문에 원래 쿠키 값은 적지 말고 `[REDACTED]`로 표시**
- `[실측 입력: 성공/실패 HTTP 상태, 시간, 쿠키 가림 확인]`

## ⑥ 아직 못 막은 것

현재 구현은 **최초 패스키를 모두 잃어버렸을 때 본인을 안전하게 복구하는 독립된 신원 확인 절차**를 제공하지 않습니다. 마지막 패스키 삭제를 거절하지만 기기 고장·분실까지 막지 못하므로, 서로 다른 장치 또는 보관 수단으로 키 두 개를 등록해야 합니다. 서버 측 **IP별 요청 횟수 제한과 지속적인 보안 감사 로그**도 아직 추가하지 않았습니다. 따라서 대규모 서비스 수준의 로그인 시도 제한이나 감사 추적을 보장하지 않습니다.
