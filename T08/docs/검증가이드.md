# T08 브라우저 개발자 도구 실증 가이드

> **실습 재현용 가이드 / 최종 상태 아님:** 아래 코드는 과제의 보안 요청을 재현하기 위한 예시입니다. 실제 수행한 C23·C25·C30·C31·C33·C39·C44·C45·C46 결과는 [검사결과](검사결과_2026-10-21.md)에 정리했습니다. 최종 서명 검사는 이 가이드의 `window.fetch` 임시 변조 대신 **Chrome WebAuthn 가상 인증기에서 실제 응답을 만들어 요청**하는 방법을 사용했습니다. 이미 확인한 패스키 삭제 실험을 다시 수행할 필요는 없습니다.

## 0. 준비

- HTTPS 고정 프로덕션 주소로 접속합니다. Chrome 또는 Edge에서 개발자 도구 `F12 → Network → Preserve log`를 켭니다.
- 표기: `owner`는 내 실습 계정, `reviewer`는 검증 계정, 두 계정 기록은 모두 가상 데이터입니다.
- **Network 내보내기 HAR에는 쿠키·세션·초대 링크가 포함될 수 있으므로 원본 HAR 파일을 제출하지 말고 비밀값을 가린 요청·응답 발췌만 사용**합니다.
- 아래 콘솔 검증 코드는 **자신의 T08 배포 사이트에서만** 실행합니다. 저장/삭제 API 검사는 본인의 실습 계정에만 수행합니다.

## 1. 공개 HTML / 401

- 시크릿 창에서 `/` 접속 → 원본 T01 소개, 비공개 잠금 화면이 보임.
- `view-source:https://배포주소/`에서 `가상 프로젝트 A:` 등의 **비공개 실제 문장**이 보이면 안 됨.
- 무로그인 콘솔:

```javascript
const noAuth = await fetch('/api?action=notes', {credentials:'omit',cache:'no-store'});
console.log(noAuth.status, await noAuth.json()); // 예상 401
```

## 2. 등록 challenge 비교 (owner 로그인 후)

```javascript
async function post(action, body={}) {
  const res=await fetch('/api?action='+action,{
    method:'POST',credentials:'same-origin',headers:{'Content-Type':'application/json'},
    body:JSON.stringify(body)
  });
  return { status:res.status, data:await res.json() };
}
const regA=await post('registration-options');
const regB=await post('registration-options');
console.log(regA.status,regB.status,regA.data.options?.challenge !== regB.data.options?.challenge);
// 예상: 200, 200, true. challenge 원문은 민감 데이터가 아니라 일회용 공개 질문.
```

인증 창의 중간 취소: UI의 `패스키 추가 등록` 버튼을 눌렀다가 기기 팝업에서 취소합니다. 화면에 취소 안내가 나오고, 패스키 목록 개수가 증가하지 않아야 합니다.

## 3. 로그인 challenge 비교 및 위조 인증

```javascript
const loginA=await post('authentication-options',{handle:'owner'});
const loginB=await post('authentication-options',{handle:'owner'});
console.log(loginA.status,loginB.status,loginA.data.options?.challenge !== loginB.data.options?.challenge);
const tamper=await post('authentication-verify',{
  challengeId:loginA.data.challengeId,
  response:{id:'등록되지-않은-가짜-id',type:'public-key',response:{}}
});
console.log(tamper.status,tamper.data); // 예상 403
```

**서명이 실제로 검증되는지 별도 확인(등록된 키의 서명을 변조):** 실제 소유 계정에서 로그인하기 전, 같은 사이트의 개발자 도구 Console에 아래 코드를 한 번 실행합니다. 이어 평소와 똑같이 패스키로 로그인을 시도하면 **새 challenge에 대한 실제 서명이 브라우저에서 생성된 뒤 첫 검증 요청의 서명 한 글자만 바뀝니다.** 서버가 `403`을 반환해야 합니다. 검사 후 반드시 원래 `fetch`로 복구합니다. 이 검사는 앞의 **미등록 ID 403**과 다르게 서명 검증 자체를 시험합니다.

```javascript
const originalFetchForSignatureTest = window.fetch;
window.fetch = (url, options) => {
  if (String(url).includes('action=authentication-verify') && options?.body) {
    const body = JSON.parse(options.body);
    const signature = body.response?.response?.signature;
    if (typeof signature === 'string' && signature.length > 0) {
      body.response.response.signature = (signature[0] === 'A' ? 'B' : 'A') + signature.slice(1);
      return originalFetchForSignatureTest(url, { ...options, body: JSON.stringify(body) });
    }
  }
  return originalFetchForSignatureTest(url, options);
};
// 이제 실제 페이지의 패스키 로그인 버튼을 누릅니다. 응답 403 확인 후:
// window.fetch = originalFetchForSignatureTest;
```

**주의:** 브라우저 콘솔을 새로고침하거나 위 복구 명령으로 되돌린 뒤 정상 로그인을 진행하세요. 실제 성공 기록도 따로 남겨야 합니다. 응답의 서명·쿠키 원문은 제출하지 말고 상태 코드와 가려진 발췌만 기록합니다.

실제 성공/재사용 409 증명: 패스키 로그인 시 정상 `authentication-verify` 요청을 Network에서 열고 **성공 JSON을 동일 challengeId와 함께 다시 전송**합니다. DevTools의 요청 다시 보내기를 사용하세요. **동일 요청을 재사용하면 예상 409**, 새 질문을 얻으면 다른 값입니다. 원시 세션 쿠키는 기록에서 삭제합니다.

## 4. 다른 계정에 대한 거절 (owner로 로그인)

```javascript
const own=await fetch('/api?action=account-notes&account=owner').then(async r=>({status:r.status,data:await r.json()}));
const other=await fetch('/api?action=account-notes&account=reviewer').then(async r=>({status:r.status,data:await r.json()}));
const fakeQuery=await fetch('/api?action=notes&account=reviewer').then(r=>r.json());
const fakeBody=await post('notes',{account:'reviewer'});
console.log('내 계정',own.status,own.data.items?.length); // 예상 200, 3
console.log('타 계정 거절',other.status);             // 예상 403
console.log('주소 위조 후 실제 소유자',fakeQuery.owner); // owner
console.log('본문 위조 후 실제 소유자',fakeBody.data.owner); // owner
```

로그아웃하고 `reviewer` 계정에서 같은 코드를 반대로 실행하세요. 거절 전후 owner/reviewer 메모 개수 모두 3건이어야 합니다.

## 5. 삭제 뒤 로그인 및 마지막 키

- owner로 로그인 → 패스키 이름과 등록일 2개 스크린샷 → 키 A 삭제 → 키 B만 남는지 확인.
- 로그아웃 → 키 B로 로그인 성공 → 내 기록 3개 확인.
- 키 A의 credential ID로 `authentication-verify`를 보내려 하면 403 (신규 질문을 먼저 받은 후 제출). 삭제한 키가 브라우저 저장소에는 남아도 서버에서 인정하지 않음.
- 마지막 키 B 삭제 요청은 `409`로 거절되어 복구 불능을 방지함.
- **패스키가 하나도 없는 초기 reviewer 계정**은 로그인 옵션 요청에 `409` 및 `등록된 패스키가 없습니다` 안내. 새 최초 초대가 있어야 등록 가능.

## 6. 로그아웃 세션 재사용

개발자 도구에 남은 기존 요청의 세션 쿠키를 **별도로 제출하지 말고 내부에서만** 재전송합니다. 로그아웃 전 비공개 API `200`, 로그아웃 후 같은 값 사용 시 `401`이어야 합니다. 새 세션은 재로그인 후에만 발급됩니다.


## 2026-10-21 실제 실행 결과

- 사용자 실기기: 아이폰 패스키로 PC QR 승인 후 본인 기록 3건 표시.
- Chrome WebAuthn 가상 인증기로 C30 서명 변조 403 → 정상 서명 200 → C31 동일 원본 재전송 409.
- C45 검사용 키 삭제 200 → 삭제 ID 인증 403, 잔여 패스키 1개.
- C33 로그아웃 후 이전 쿠키 요청 401, C39 양방향 교차 조회 403, C46 마지막 키 삭제 409.
- 개인키·서명 원문·쿠키·일회용 토큰은 공개 문서에 보관하지 않았습니다.
