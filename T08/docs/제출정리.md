## 짧은 확인 방법 4줄

- **위치:** T08 배포 주소의 공개 소개 아래 ‘비공개 자리’로 이동합니다.
- **행동:** PC에서 ‘휴대폰 패스키로 로그인’을 누르고 QR을 아이폰으로 스캔한 뒤, 아이폰에서 패스키 인증과 PC 로그인을 승인합니다.
- **통과:** PC 화면이 자동으로 로그인 상태로 바뀌고 해당 계정의 가상 비공개 기록 3건이 표시됩니다.
- **거절:** 로그인하지 않은 사용자는 비공개 기록을 열 수 없으며, 다른 계정의 기록 직접 조회는 403으로 거절됩니다.

## AI와 내 판단 3줄

- **AI에게 맡긴 일:** T01 공개 소개를 유지하면서 패스키 인증, 휴대전화 QR 승인, 서버 검증과 자동 테스트를 구현하고 점검했습니다.
- **직접 판단한 일:** PC에서 USB 보안키 선택창에 의존하지 않고 아이폰 패스키로 승인하는 방식을 선택했고, 실제 기기에서 로그인과 비공개 기록 표시를 확인했습니다.
- **따르지 않은 제안:** PC의 기본 USB 보안키 인증창에 의존하는 방식은 사용하지 않고, PC와 아이폰을 QR로 연결하는 방식으로 수정했습니다.

## 확인된 결과

- 아이폰 패스키 승인 후 PC 자동 로그인: 실제 동작 확인
- PC 및 아이폰의 비공개 기록 조회: 실제 동작 확인
- 등록 취소(C25): 패스키 수 유지 (owner 1, reviewer 2)
- 다른 계정 조회(C39): **양방향 실측 PASS** — owner→reviewer 및 reviewer→owner 각각 403, 본인 기록 조회 200·3건 유지
- **C30:** Chrome 가상 인증기에서 만든 서명의 1비트 변조 → HTTP 403, 동일한 원본 정상 서명 → HTTP 200 (실측 PASS)
- **C31:** 동일 `{challengeId,response}` 정상 인증 요청을 그대로 재전송 → HTTP 409 (실측 PASS)
- **C23:** 가상 패스키 등록 중 `registration-verify` 요청 본문 확인. 노출된 필드에 개인키 없음. 서버 공개키 보관 및 DB 확인 (일부 하위 필드 미전개)
- **C44/C45:** 가상 시험 키 삭제 및 잔여 키 재로그인 확인. 이후 생성된 가상 인증기 키를 삭제 200 → 삭제한 키로 인증 403 → 잔여 패스키 1개 (실측 PASS)
- **C46:** 마지막 키 삭제 요청 409 → 잔여 패스키 1개 (실측 PASS)
- 로그아웃(C33): 로그아웃 전 기존 쿠키 요청 HTTP 200, 로그아웃 후 같은 요청 HTTP **401 Unauthorized** 확인. **실측 PASS**
- 운영 DB: 성공적으로 소비된 QR 연결 2건, 사용된 인증 질문 12건, 철회된 세션 12건
- GitHub Actions: Node.js 22 빌드 및 테스트 **31/31 PASS**
- C23/C30/C31/C45의 시험용 키 자동 테스트와 가상 인증기 기반 운영 HTTP 검사를 수행함. 실물 아이폰은 별도 로그인·QR 연결에 사용함.
- 운영 DB 최종 상태: owner·reviewer 각각 패스키 1개, 비공개 기록 3건

## 제출 전 남은 일

1. 필요 시 C23 Payload의 접힌 하위 필드까지 펼쳐 스크린샷을 추가합니다. 실물 아이폰 패스키의 직접적인 서명 변조 재현은 실시하지 않았음을 구분합니다.
2. `main`으로 병합하고 T01~T07 배포에 영향을 주지 않았는지 확인합니다.
3. 최종 배포 주소와 소스 URL, 무로그인 공개 화면을 확인합니다.

### 보안 참고

- 실제 초대 링크·QR 토큰·세션 쿠키·서명 원문·DB 연결 문자열은 제출하지 않습니다.
- 마지막 패스키는 삭제하지 않습니다. 사용자 실물 패스키를 자동 검사 목적으로 지우지 않았습니다.
- 모든 비공개 기록은 과제용 가상 자료입니다.
