## 짧은 확인 방법 4줄

**어디로 가나요:** 결과물 주소의 공개 T01 소개를 보고, 하단의 T08 비공개 영역으로 이동합니다.

**무엇을 하나요:** ① PC에서 휴대폰 패스키 로그인을 선택하고 ② 아이폰으로 사이트 QR을 스캔하여 패스키 인증을 승인한 뒤 ③ PC의 로그인 상태와 기록을 확인합니다.

**무엇이 보이면 통과인가요:** PC에 해당 계정의 가상 기록 3건이 표시되고, 다른 계정의 비공개 API 요청은 HTTP 403으로 거절됩니다.

**안 될 때는 무엇이 보이나요:** 승인 없이 다른 계정의 내용이 보이거나, 로그아웃한 세션으로 조회해도 200이 반환된다면 실패입니다. 정상 구현에서는 무인증·로그아웃 세션 요청이 401로 거절됩니다.

## AI와 내 판단 3줄

**AI에게 맡긴 일:** T01의 공개 화면을 유지하면서 WebAuthn 서버·브라우저 인증, Supabase 계정 분리, PC QR 연동과 자동 검사의 코드·문서 초안을 작성하는 데 도움을 받았습니다.

**직접 판단한 일:** PC에서 USB 보안키 선택창으로는 아이폰의 패스키를 편하게 쓸 수 없어서 휴대폰 QR 승인 방식을 선택했습니다. 실제 아이폰으로 로그인·승인하고, PC에서 비공개 기록과 401·403·409 응답을 직접 확인했습니다.

**AI 제안을 따르지 않은 일:** USB 인증 방식을 계속 사용하는 대신 PC QR 로그인을 요구했고, 아이폰 단축어를 이용한 보안 검사도 실제로 결과를 재현하기 어려워 사용하지 않았습니다. 대신 PC에서 별도로 만든 가상 패스키로 운영 API를 검증했습니다.

## 어떻게 시험했는가

패스키 자체는 **아이폰 암호(Passwords) 앱**에 등록해 사용했습니다. PC에서 휴대폰 QR 로그인 화면을 연 다음, 아이폰에서 QR을 스캔하고 패스키 인증을 승인하면 PC에 로그인 세션이 만들어졌습니다. PC 및 아이폰에서 각각 본인 가상 메모 3건이 보이는 것을 확인했습니다. 서버에는 QR 승인 연결이 PC 로그인으로 완료된 기록도 확인했습니다.

문제는 **보안 실패 요청을 실제로 반복하는 실험**이었습니다. 아이폰의 일반 패스키 로그인 화면에서는 이미 생성한 서명의 일부만 바꾸거나 같은 서명 JSON을 그대로 두 번 제출하는 것이 어려웠습니다. 아이폰 단축어 방식도 시도했지만 결과를 안정적으로 확인하지 못했습니다. 그래서 iPhone과 똑같이 시험했다고 적지 않고, **PC Chrome DevTools의 WebAuthn 가상 인증기**를 켜서 별도의 시험용 패스키를 등록하고 실제 T08 운영 서버에 요청을 보냈습니다.

등록 요청의 보이는 Payload에는 개인키 항목이 없었고(C23), 서버 DB는 검증된 공개키만 저장했습니다. 운영 DB에서는 등록 질문 17건·로그인 질문 48건 모두 중복되지 않았습니다. 다만 C23 Network 캡처는 일부 하위 필드가 접혀 있고, 두 질문 원문을 비교하는 별도 사진 등 일부 보조 증거는 남아 있지 않습니다. 자세한 범위는 검사 문서에 표시했습니다.

**최종 보존 상태:** owner와 reviewer 각각 패스키 1개, 가상 비공개 기록 3건. 시험용 가상 패스키는 모두 삭제했습니다. 자동 테스트는 Node.js 22 환경에서 **31/31 PASS**입니다.

## 첨부·증거 관리

검사 중 확인한 브라우저 응답 표와 Network Payload는 민감한 정보(쿠키·원시 서명·초대 링크·QR 토큰)를 제외한 캡처만 제출합니다. GitHub에 있는 문서 자체가 모든 캡처 파일을 포함한다는 뜻은 아닙니다. 해당 캡처는 검증을 진행한 대화에서 별도로 확인했습니다.

**남은 것은 제출 사이트의 입력란에 결과물/소스 URL을 입력하고, 요구하는 경우 캡처를 직접 첨부하는 절차입니다.** 이미 성공한 패스키 삭제·변조 검사를 다시 할 필요는 없습니다.
