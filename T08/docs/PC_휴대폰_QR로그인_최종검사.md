# T08 아이폰 패스키와 PC WebAuthn 시험 기록

**2026-10-21 실험 완료 기록.** 이 문서는 이미 수행한 절차와 결과를 남기기 위한 문서이며, 추가 실행 지시서가 아닙니다.

## 1. 시작한 문제와 변경 이유

T08의 핵심은 비밀번호가 아니라 WebAuthn 패스키로 비공개 영역을 열고, 개인키를 웹사이트 서버에 보내지 않는 것이었습니다. 초기 구현은 PC에서 로그인 버튼을 누르면 브라우저의 기본 WebAuthn 인증창이 열리는 방식이었습니다. 그러나 실제 패스키가 저장된 장치는 **아이폰**이었고, Windows PC에서는 USB 보안키를 찾거나 인증을 취소했다는 메시지가 표시되어 반복 검증하기 어려웠습니다.

처음에는 PC에서 그대로 인증하거나 아이폰 단축어를 이용해 검사해 보려고 했습니다. 단축어는 Safari의 실행 결과가 제대로 전달되지 않아 테스트용 원본 서명을 안정적으로 재사용하는 용도로 부적합했습니다. 이 시점에 **일반 로그인 경로**와 **서명 보안성 실험 경로**를 분리하기로 했습니다.

- 실제 접속을 위한 로그인: **PC가 사이트 자체 QR을 표시 → 아이폰으로 스캔 → 아이폰 패스키 승인 → PC 자동 로그인**.
- 공격·재사용을 재현하는 실험: **PC Chrome DevTools WebAuthn 가상 인증기에서 별도 키 생성**, 운영 API에 변조·재전송 요청을 전송.

이렇게 나누면 실제 사용자 패스키를 고의로 삭제하거나 비정상 응답으로 반복 소모할 필요가 없고, 아이폰 저장 방식도 유지할 수 있었습니다. 단, 가상 인증기로 측정한 결과를 아이폰 실기기에서 직접 수행했다고 기록하지 않았습니다.

## 2. QR 로그인 구현과 실제 성공

PC에서 휴대폰 로그인 버튼을 누르면 서버의 `phone-start`가 PC 전용 HttpOnly 쿠키와 QR 일회용 토큰을 각각 만들고 해시만 DB에 저장합니다. 아이폰은 QR 토큰으로 `phone-prepare`를 호출한 뒤 WebAuthn 질문에 서명하고, `phone-approve`로 승인을 요청합니다. 승인했다고 휴대전화에 PC 세션이 전달되는 것이 아닙니다. PC가 자기 쿠키로 `phone-poll`을 호출했을 때만 대기 중이던 승인을 **원자적으로 1회 소비**하여 PC에 세션을 발급합니다. QR 연결은 3분 뒤 만료됩니다.

실제 검사에서는 PC의 QR을 아이폰으로 열고 패스키 인증을 승인하자 PC 화면이 자동 로그인 상태로 바뀌었으며 **owner 본인 가상 기록 3건**이 표시됐습니다. 아이폰에서도 reviewer 계정으로 로그인해 **reviewer 기록 3건**을 확인했습니다. Supabase에서 **승인 후 PC가 소비한 QR 연결 2건**을 확인했습니다. 이는 성공한 횟수의 DB 집계이며 화면에서 캡처한 로그인 결과와 구분했습니다.

## 3. PC 가상 인증기를 별도로 사용한 이유

아이폰 Safari에서 일반 WebAuthn 인증은 할 수 있지만, 과제의 C30·C31은 정상 인증 응답 JSON을 보유한 상태에서 **서명을 한 비트 바꾸거나 동일 요청을 한 글자도 수정하지 않고 다시 전송**해야 합니다. 실물 아이폰의 일반 인증창은 이를 위한 개발자 도구가 아니었고, 단축어 방식도 안정적인 증거를 얻지 못했습니다.

그래서 PC Chrome 개발자 도구 `F12 → WebAuthn`에서 다음 조건으로 **시험용 가상 인증기**를 추가했습니다.

| 설정 | 값 |
| --- | --- |
| Protocol | CTAP2 |
| Transport | internal |
| Resident key | 지원 |
| User verification | 지원·검증 활성화 |
| Automatic presence simulation | 활성화 |

가상 인증기로 `reviewer`에 추가 패스키를 정상 등록하고, 실제 운영 DB에 **공개키가 저장되고 패스키 수가 증가**한 것을 확인했습니다. 이 등록도 실제 T08 운영 서버의 `registration-verify` API를 거쳤습니다. 가상 인증기는 Chrome 개발자 도구에서 사용하는 시험용 수단이므로, 실제 아이폰 패스키의 저장 위치를 바꾸거나 개인키를 앱 서버에 올리는 작업이 아니었습니다.

## 4. 실제 HTTP 실험 순서와 결과

| 순서 | 수행 과정 | 정상 기대 | 관찰 |
| --- | --- | --- | --- |
| C23 | 검사용 가상 키 등록 후 Network의 `registration-verify` 요청 Payload 확인 | 공개키 기반 등록·개인키 미전송 | 등록 성공; 노출 필드에 개인키 없음, DB 공개키 저장 |
| C30-1 | 가상 인증기로 정상 서명을 생성한 뒤 마지막 바이트의 한 비트를 바꿔 전송 | 변조 서명 거절 | **403** |
| C30-2 | 변조 전 원본 `response`와 같은 `challengeId`로 인증 | 유효 서명 승인 | **200** |
| C31 | 성공 요청과 완전히 동일한 `{challengeId,response}` 재전송 | 사용된 질문 재사용 거절 | **409** |
| C45-1 | 새 가상 시험용 키로 서명을 생성한 뒤 해당 키를 서버에서 삭제 | 삭제 성공 | **200** |
| C45-2 | 삭제된 키의 credential ID 및 확보한 서명으로 인증 요청 | 등록 목록에서 삭제된 키 거절 | **403** |
| C45-3 | reviewer 키 목록 재조회 | 실제 아이폰 키 1개 보존 | **1개** |

C30의 403은 등록되지 않은 임의 ID만 넣어 보는 검사가 아니라, **서버에 등록된 시험용 공개키에 대응하는 정상 서명 자체를 변조한 결과**입니다. 변조 요청은 challenge를 성공 소비하지 않았으므로 이어서 정상 원본을 제출할 수 있었습니다. 이후 C31에서는 정상 요청이 이미 사용한 challenge였으므로 똑같은 원문을 보내 409를 확인했습니다.

C45에서는 **서명을 먼저 받아 둔 다음 가상 키를 삭제**했습니다. 삭제 후에는 더 이상 서버의 키 목록에 해당 ID가 없으므로 403이 반환됐습니다. 따라서 “삭제된 키가 모바일에서 선택창에 안 뜬다”는 것만 보여 준 검사가 아니라 **운영 서버의 인증 거절 경로**를 확인했습니다.

## 5. 아이폰 패스키와 사용자 자료가 남아 있는지 확인

- **C25:** 패스키 추가 등록을 중간 취소한 뒤 등록 수가 그대로인지 확인했습니다.
- **C33:** 로그아웃 직전의 쿠키로 요청을 다시 보냈을 때 HTTP **401**을 확인했습니다. 처음에는 로그아웃을 누르지 않은 상태로 검사해 200을 보았지만, 로그아웃 후 동일 요청을 재실행해 정상적으로 401임을 확인했습니다.
- **C39:** owner→reviewer, reviewer→owner 타인 기록 요청 모두 **403**. 전후 본인 기록은 **200 및 3건**으로 그대로였습니다.
- **C44:** reviewer에 등록됐던 `테스트2 패스키`를 삭제한 뒤 남은 아이폰 패스키로 다시 로그인하여 reviewer 기록 3건을 확인했습니다.
- **C46:** 마지막 등록 키 삭제 시도는 **409**, 키 1개 유지.
- **DB 최종 확인:** owner와 reviewer 각각 실제 패스키 **1개** 및 비공개 기록 **3건**.

테스트용 키는 나중에 정리하더라도 브라우저의 개발자 도구가 기존 실제 아이폰 키를 대체하는 것은 아닙니다. 서버에서 시험용 가상 패스키만 삭제했고, 최종 DB에 두 실습 계정의 정상 사용 키가 남아 있음을 확인했습니다.

## 6. 제출할 때 표시할 한계

- C23의 등록 요청 Payload 화면에는 `challengeId`, `label`, `response`, `rawId` 등이 보였지만 `response` 하위 필드는 일부 접힌 상태였습니다. **관찰하지 못한 하위 필드까지 직접 봤다고 주장하지 않습니다.** 서버 DB에서 공개키 저장과 개인키 미저장 구조를 확인했습니다.
- 등록 질문 **17건 모두 서로 다른 값**, 로그인 질문 **48건 모두 서로 다른 값**임을 DB의 중복 없는 건수 집계로 확인했습니다. 두 질문의 전체 문자열을 나란히 게시하지는 않았습니다.
- 서명 변조·재전송·삭제 키 요청의 **403/200/409/403은 PC Chrome 가상 인증기가 실제 운영 서버에 보낸 결과**입니다. 실물 아이폰에서 해당 비정상 요청을 실행했다는 의미는 아닙니다.
- 서버에 공개되는 문서에는 원래 세션 쿠키, 서명 JSON, QR 토큰, 일회용 등록 초대 링크, DB 접속 문자열을 포함하지 않았습니다.
- Node.js 22 자동 검사 **31/31 PASS**는 별도로 수행한 코드 회귀 검사입니다. 이 숫자만으로 운영 서버의 HTTP 보안성을 판정한 것은 아닙니다.
