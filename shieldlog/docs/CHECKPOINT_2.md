# ShieldLog — 중간 점검 2차 제출용 문안

> 2026-11-06 기준, 실제 구현과 도구로 수행한 검증만 적었습니다. Workbench 제출 버튼은 사용자가 직접 눌러야 합니다.

## 이번에 만든 것

1차에서 약속했던 CSV·JSON 파일 가져오기, 보안 사건별 상태(미확인·조사 중·조치 완료)와 조사 메모 저장, 화면 재로드 후 복원, 원본 이벤트 검색, Markdown 분석 보고서 및 CSV 다운로드를 검증하고 정리했습니다. 390px 모바일 화면의 메뉴 전환도 확인했습니다. 아울러 상태코드가 누락된 로그를 잘못 정상 응답(200)으로 표시하던 부분을 `N/A`로 수정했습니다. 샘플 로그 150건을 이용한 탐지 사건 4건 표시도 유지됩니다.

## 확인하는 방법 (3단계 이내)

1. `https://shieldlog-premium.vercel.app/` 에 접속한 뒤 **로그 가져오기**에서 CSV 또는 JSON 샘플 파일을 선택해 이벤트 150건과 탐지 사건 4건이 표시되는지 확인합니다.
2. **탐지된 사건**에서 한 사건을 열고 **조사 중** 상태와 메모를 저장한 뒤 다시 불러와 같은 상태와 메모가 표시되는지 확인합니다.
3. **사건 보고서 내보내기**로 Markdown 파일을 다운로드하여 조사 메모를 확인하고, **원본 이벤트**에서 IP 검색과 CSV 다운로드를 확인합니다.

## 바뀐 점과 이유

1차에는 기본 대시보드와 4종 탐지 결과를 확인했다면, 2차에는 실제 분석자가 사용하는 파일 가져오기→사건 조사→기록 복원→보고서 내보내기의 전체 흐름을 검증했습니다. 확인 과정에서 HTTP 상태값이 없는 로그를 성공 응답으로 표시하는 오류를 수정하여 분석 결과의 의미를 명확히 했습니다. 외부 서버에 민감한 로그를 전송하지 않는 브라우저 로컬 처리 방식은 유지했습니다.

## AI에게 맡긴 일과 내가 판단한 일

AI에게 CSV·JSON 입력, 사건 상태와 메모 저장, Markdown·CSV 내보내기, 모바일 동작 점검과 자동 테스트를 맡기고, 검증 중 확인한 상태코드 표시 문제를 수정하게 했습니다. 저는 보안 이벤트 탐지·분석이라는 프로젝트 방향을 선택하고, 1차에서 정한 기능을 실제 동작으로 검증하도록 요청했습니다. 실제 침해 여부를 확정하는 앱이 아니라는 한계는 유지하며, 최종 제출 여부는 직접 판단합니다.

## 다음에 할 일

공개된 앱에서 파일 가져오기와 사건 기록이 정상 작동하는지 최종 확인하고, GitHub의 `shieldlog/` 폴더 및 계획서 `plan.md` 최신 버전을 확인한 뒤 최종 제출 자료를 정리하겠습니다. 실제 사용자 반응은 별도 확인 후 기록하겠습니다.

## 사용자에게 확인받은 결과

현재 외부 사용자 또는 제출자가 앱을 직접 사용한 후 남긴 피드백은 수집하지 않았습니다. 대신 Chromium 브라우저를 자동 조작하는 검증에서 PC·모바일 화면의 정상 표시, 2가지 파일 가져오기, 조사 기록 복원, 보고서 다운로드 및 검색을 확인했습니다. 누락된 상태코드 표시 문제를 발견해 수정했으며, 수정 후 테스트에서 재발하지 않았습니다. 자동 테스트 결과를 실제 사람의 사용 후기로 대신하지 않았습니다.
